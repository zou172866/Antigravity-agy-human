# `wait-what` — 通俗但不失真的技术复述与代码拆解

当用户对前文解释感到困惑、卡在复杂源码/报错上，或明确要求「说人话 / 重讲 / 费曼拆解」时执行本流程。

## 核心纪律（防止为了通俗而失真）

1. **先补上下文，再讲当前点**：默认用户可能丢了前提；先用 1～2 句交代「我们现在在解决什么问题、卡在哪个环节」。
2. **先机制，后术语（Mechanism before Name）**：先用直白动作描述“发生了什么”，再贴上准确的专业名词（例如先说“旧请求返回更慢，后到反而把新数据盖掉了”，再标注“异步竞态 / Race Condition”）。
3. **对齐项目真实词汇**：若当前工作区存在 `CONTEXT.md`、`GLOSSARY.md`、`README.md` 或 `AGENTS.md`，优先沿用项目内的真实模块名与领域名词，不自造同义词。
4. **简明技术句法（借鉴 ASD-STE100）**：
   - 一句只说一件事，主动语态，主语明确（少用“进行了相关处理”这类模糊表达）。
   - 严禁“降智”删细节：文件路径、函数名、关键变量、状态流转与精确报错必须原样保留。
5. **类比必须交代失效边界**：若引入生活类比，紧跟两件事——**映射回真实代码对象**，并明确指出**这个类比在什么地方不再适用**（避免建立错误的心智模型）。

## 标准输出结构（三层阶梯，按需精简）

### 1. 一句话定位（上下文 + 结论）
用 1～2 句大白话回答：现在在干嘛、核心问题/核心结论是什么。

### 2. 人话拆解机制（直觉层）
- 用短句按因果或时间顺序讲清“数据/控制流是怎么走的”。
- 仅在能显著降低理解门槛时补一个生活类比，并立刻写出：
  - **代码映射**：类比中的 A = 代码里的 `xxx`，B = `yyy`。
  - **类比边界**：真实系统与类比的关键差异（如并发、持久化、重试或内存语义）。

### 3. 技术锚点与易踩坑（精度层）
- **关键位置**：列出精确的文件路径、函数/类/配置符号及核心分支逻辑（不逐行翻译代码）。
- **为什么这么写 / 权衡（Why & Trade-off）**：说明设计意图或选择当前方案的原因。
- **最容易误解的点（防自欺检验）**：指出 1～2 个常见误区、边界条件或潜在失败模式。

## 执行检查
- 复述完后，如仍有多个复杂子模块，最后用一句话问用户想继续深挖哪一块，不要一次性倾倒无关细节。
