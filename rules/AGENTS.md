# 实时编程表达规范（通俗与技术精度平衡）

目的：让用户在实时编程中第一眼看懂意图、变化与风险，同时保留排错、Code Review 与溯源所需的全部精确技术细节。

## 1. 自适应详略（不拖慢节奏）
- **简单改动 / 明确问答**（1～2 处小修、单点查询）：保持极简，直接给「一句话结论 + 改动位置/命令 + 验证结果」，不展开长篇科普。
- **复杂任务**（多文件改动、Bug 排查、架构/方案决策、原理分析）：按下方分层结构输出。

## 2. 先人话结论，再给技术锚点（倒金字塔）
- **顶层（结论层）**：开头 1～2 句用直白短句（一句只说一件事、主动语态）讲清「解决了什么问题 / 行为发生了什么变化」，去掉寒暄与空洞套话。
- **底层（技术层）**：紧跟结构化条目，**逐字保留**精确文件路径、函数/类名、配置键、关键参数、原始错误码与实际执行的验证命令及结果，不得因通俗化而省略或模糊。

## 3. 保留术语、就地翻译，不靠模糊类比替代事实
- 保留准确的工程术语（如竞态条件、幂等性、缓存失效），不在专业精度上“降智”。
- 遇到关键或易混淆机制首次出现时，先用直白短句点透机制，再括号标注对应专业术语（或术语旁紧跟一句白话释义）。
- 仅在明显有助于理解时使用类比，且**必须立即把类比映射回真实代码对象**，避免误导。

## 4. 讲「为什么（Why）」和「取舍」，不复读 Diff
- 代码 Diff 已展示改了哪行，重点说明：**根因是什么、为何选此方案而非替代方案、隐含假设及已知边界/技术债**。
- 复杂改动或关键决策处，可附 1～2 句简短的 `**要点**` 说明设计原因。

## 5. 过程简报，收尾自包含
- 多步执行过程中，在关键里程碑用一句大白话同步进度与下一步，不刷屏原始长堆栈。
- 最终回复去流水账（不堆砌中途试错过程），收敛为可独立阅读的闭环：**结论 → 根因与改法 → 验证结果 → 边界/下一步**。
